The rules it cannot break

  • Every claim is checked against a committed receipt. A card pins one JSON receipt by repo, full commit and sha256; every number in the post must be a named field of it; a number from a claim that failed is refused; no hype, no prices, no economy talk.
  • Nothing leaves without Simon's approval of the exact words. The approval names the post and the sha256 of its text — change one character and it no longer counts. A rehearsal approval can only ever authorise a dry run.
  • Replies only when summoned. Someone @mentions us, we answer once, opt-outs honoured. This is also exactly where X draws its own line for automation.
  • Hard daily cap (… a day) — a voice, not a firehose.
  • No near-duplicates — shingle overlap against everything ever posted or queued; … or more is refused.
  • Dry-run by default. Without the owner's keys and an explicit switch, nothing leaves the machine — and this page shows the rehearsals anyway.

  • Technology and security: no dependencies to patch, keys only in the machine's environment (measured: never written or printed), two outbound hosts, kernels mutation-gated in CI, and source you can read end to end.

    Security and data protection

    • It runs on your machine. Plain Node with no third-party packages; there is no server of ours in the path, and nothing phones home.
    • Two outbound hosts, both named in the code. The voice fetches receipts from raw.githubusercontent.com at pinned commits, and, only when live, sends the approved text to api.x.com. This page fetches its own files, the same receipts, and the CI status badge image from github.com; no analytics, no cookies, no third-party scripts.
    • The keys stay in your environment. Four variables (X_CONSUMER_KEY, X_CONSUMER_SECRET, X_ACCESS_TOKEN, X_ACCESS_SECRET) the owner sets; the code reads them only to sign the request to X. Measured with planted fake keys through every sealed run: ….
    • Almost no personal data. It handles your published receipts and the text of your posts, and reads no customer or prospect data. The only personal data it keeps is the approver's name and quoted words in the approval file, which is public in this repo; keep your deployment's repo private if you want those words private.
    • No one else in the path. The only services involved are your own GitHub (the repo, the receipts and this page) and, once live, your own X account. AI Native Solutions holds none of your data and runs no service the voice depends on.
    • It fails closed. If GitHub cannot be reached, or a receipt is not the file the card pinned, the card is refused and nothing posts; if X refuses a post, nothing is recorded as posted.
    • Cutting it off is one step. Remove the four variables (or regenerate them at X) and nothing can post; node voice.mjs withdraw <id> cancels an approval before it is used.
    • Everything is on the record. The queue, the approvals and the ledger are files in git, so every change to them is in the repository's history. It runs on Node.js (the version CI runs is named in .github/workflows/gate.yml).
    • Tamper-evident by construction. A card pins a full commit and the receipt's SHA-256; a receipt edited after the fact no longer matches and the card is refused. An approval is bound to the SHA-256 of the exact text; one changed character voids it.
    • It cannot cold-message anyone. That code does not exist in the repo.

    Adoption — how a team rolls it out

    1. Take a copy. Fork the repo (MIT), or have AI Native Solutions set it up with you.
    2. Point it at your organisation. claim-gate.mjs names this estate's GitHub organisation (the receipt repos and the link hosts it accepts) and its approver; set yours, and push — CI re-runs the tests and the mutation gate on your change.
    3. Write receipt cards in feed.jsonl for results your teams already commit: repo, full commit, path, the file's SHA-256, and the fields each number comes from.
    4. Run it dry. node voice.mjs draft, publish this page on your own GitHub Pages, and let the team watch the queue and the refusals for a while.
    5. Name the approver (communications lead or founder). Approvals are recorded with their words, one post at a time.
    6. Turn the key when ready. The owner adds the four X variables to the machine's environment and sets DRY_RUN=0; node voice.mjs post <id> posts one approved item.

    Risks, straight

    • The gate checks numbers, not fairness. It proves each number is the receipt's number at a named field; whether the sentence around it is fair is what the approval of the exact text is for.
    • One approver, by design. When that person is away, posts wait, urgent ones included.
    • Receipts must be public. The gate fetches them from GitHub so anyone can re-fetch them; a private result cannot be cited.
    • It can refuse a fair post. A post too like an earlier one is refused (X refuses them too) — reword it or let it wait. A claim whose receipt failed is refused even if the number is right.
    • X sets the terms. If X changes its rules, prices or API, posting may stop; the drafting, the gates, this page and the ledger keep working.
    • An approval is a record, not a signature. Kar writes it on the approver's word, quoted; whoever can write to the machine or the repo could add one. Guard the approval file like the keys: the same people should hold both.
    • No third-party certification is claimed. The evidence is the source itself, the mutation gate that runs on every push, and the sealed measurement with its failure kept.
    • It has not posted live yet. The ledger above shows rehearsals only until the owner adds the keys. Its evidence today is the sealed measurement, failure included.

    White paper — proof before speech

    The problem. A company's public claims drift from its evidence: a figure gets rounded up, a result that failed gets quoted anyway, a draft is edited after it was signed off. Language models make drafting cheap, which makes the drift faster. And X's automation rules draw a hard line around unsolicited automated replies.

    The design. Two rules, enforced in code before any key is involved. First, a post may only state what a committed receipt states: the card pins the receipt by repository, full commit, path and SHA-256, names the field behind every number, and is refused if a field is missing, differs, or sits inside a claim marked failed. Second, nothing leaves without a person's approval of the exact words, bound to the SHA-256 of the text. Drafting is a fixed template, not a model, so what is checked is what is posted. Around both sit the platform rules: length counted the way X counts it, a daily cap, near-duplicate refusal, replies only when summoned, and a dry run by default.

    The evidence. The claims were sealed before the gate's code was written, then measured once and kept: …. The measurement fetches every receipt at its pin, builds forgeries by a fixed mechanical rule (so they cannot be chosen to suit the gate), and runs the approval scenarios in a sandbox with X replaced by a recorder. CI repeats it on every push and requires the same receipt byte for byte; the failure stays on the record.

    Questions people ask first

    Does the near-duplicate check really work? …

    Where are the X keys kept? In the environment of the machine that runs the voice — the four variables above, set by the owner himself. The code reads them only to sign the request to X; it never writes them to a file, a log or this page (measured: claim V6).

    What about something urgent? It goes through the same queue: drafted, checked, and out the moment the owner approves those words. There is deliberately no way to post without him.

    Who approves, and how? Simon, in chat. Kar records his word, quoted, against the hash of the exact text (node voice.mjs approve <id> --quote "…"); the record is not a signature by Simon, and the seal says so.

    Words used here. witness: the company's mutation gate — it breaks code on purpose to prove the tests would notice. receipt: a JSON file of measured results, committed to a public repo. sealed claims: what a piece of work must achieve, committed before the code that measures it — so the bar cannot move after the fact; each is then marked held or FAILED, and failures stay. dry run: everything happens except the call to X, and the would-be post is written to the ledger as a rehearsal.
